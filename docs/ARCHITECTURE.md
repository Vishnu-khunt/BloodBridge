# BloodBridge — Architecture & Technical Design

BloodBridge utilizes a hybrid **On-Chain / Off-Chain Architecture** designed to optimize transaction throughput, data confidentiality, and verifiable immutability:

## 2. On-Chain vs. Off-Chain Separation of Concerns

| Attribute | On-Chain (Solidity Contracts) | Off-Chain (Backend & PostgreSQL) |
| :--- | :--- | :--- |
| **Data Stored** | Organization verification status, pseudonymized request hashes (`0x...`), audit batch root hashes | Full user profiles, patient referral IDs, batch shelf-life dates, geographic coordinates |
| **Privacy / PII** | **Zero PII**: No names, phones, or clinical histories | Encrypted at rest, access controlled via RBAC |
| **State Transitions** | Verification, Allocation, Dispatch, Fulfillment, Revocation | Sub-millisecond queue sorting, candidate distance calculation |
| **Cost & Latency** | Optimized gas usage (events, hashes, compact structs) | Immediate HTTP responses (< 50ms) |

## 3. Explainable Ranked Matching Algorithm

The matching engine ranks potential blood sources using a multi-factor weighting formula:

$$\text{Final Score} = S_{\text{compat}} + B_{\text{inventory}} + S_{\text{dist}} + S_{\text{fresh}} + B_{\text{urgency}}$$

### 1. ABO / Rh Compatibility Score ($S_{\text{compat}}$: 0 to 100)
- **Packed Red Blood Cells & Whole Blood**:
  - Exact match: **100 points**
  - Universal donor (O-): **90 points**
  - Compatible group (e.g. O+ into A+): **80 points**
  - Incompatible: **Excluded (0 points)**
- **Plasma & Platelets**:
  - Dynamic inversion applied: **AB is universal plasma donor**, **O is universal recipient**.

### 2. Inventory Priority Bonus ($B_{\text{inventory}}$: +25 points)
- Verified cold-storage blood bank units receive an immediate **+25 points bonus** over voluntary donors because blood bank units are pre-screened, cross-typed, and available for immediate courier dispatch.

### 3. Proximity Score ($S_{\text{dist}}$: 0 to 25)
- Calculated via the Haversine formula over geographic coordinates:
  $$d = 2R \arcsin\left(\sqrt{\sin^2\left(\frac{\Delta \phi}{2}\right) + \cos(\phi_1)\cos(\phi_2)\sin^2\left(\frac{\Delta \lambda}{2}\right)}\right)$$
- Full score (25 pts) for $\le 5$ km, decaying smoothly to 0 pts at $> 50$ km.

### 4. Freshness Score ($S_{\text{fresh}}$: 0 to 15)
- Evaluates `availability_confirmed_at` for donors:
  - Confirmed within 24 hours: **+15 points**
  - Confirmed within 7 days: **+8 points**
  - $> 7$ days: **0 points**

### 5. Clinical Disclaimer
Every ranking response generated by the matching engine includes an immutable disclaimer:
> *"This algorithmic matching score is for logistical screening only. Clinical laboratory cross-matching and compatibility assays are mandatory prior to transfusion."*

## 4. Security Intelligence Architecture

The backend inspects telemetry in real time against three rule definitions:

### Rule 1: High-Frequency Scraping / Surveillance
- **Trigger**: $\ge 15$ donor search requests within a rolling 5-minute window from a single IP or actor.
- **Threat Mitigated**: Bulk harvesting of donor demographics or geographic tracking of blood inventories.

### Rule 2: Brute-Force Authentication Defense
- **Trigger**: $\ge 5$ consecutive failed login attempts within 10 minutes.
- **Threat Mitigated**: Credential stuffing and unauthorized role takeover.

### Rule 3: Unaccredited Organization Privileged Operations
- **Trigger**: An organization with `pending` or `revoked` status attempting to reserve inventory or create emergency requests.
- **Threat Mitigated**: Rogue clinics or unauthorized intermediaries attempting to inject uninspected blood products into the network.

## 5. Cryptographic Audit Anchor & Tamper Detection

1. **Canonical JSON Serialization**: Audit log records have diverse nested metadata (e.g. `details`). Standard `JSON.stringify` does not guarantee key ordering across engines. BloodBridge uses a recursive `canonicalizeObject` helper that sorts all dictionary keys alphabetically at all nesting levels.
2. **Merkle Batch Root Hash**: A sha256 leaf hash is computed for each canonical record. Leaves are aggregated sequentially into a root hash:
   $$\text{Leaf}_i = \text{sha256}(\text{CanonicalRecord}_i)$$
   $$\text{BatchRoot} = \text{sha256}(\text{Leaf}_1 \parallel \text{Leaf}_2 \parallel \dots \parallel \text{Leaf}_n)$$
3. **Smart Contract Verification**: When `verifyAuditBatch(batchId)` is invoked, the service loads the persisted records, recalculates the root hash from scratch, and compares it against `BloodBridgeAuditAnchor.sol`. If any single byte or timestamp was modified in the database, the check fails with a tamper warning.
